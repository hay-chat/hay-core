# WhatsApp Cloud API technical brief for Hay (multi-tenant SaaS) — as of 2026-10-21

Scope note: Meta moved the WhatsApp docs to `developers.facebook.com/documentation/business-messaging/whatsapp/...` (old `/docs/whatsapp/...` URLs mostly 404 or redirect). The machine-readable index is `https://developers.facebook.com/documentation/business-messaging/whatsapp/llms.txt`. Current Graph API version is **v26.0** (released 2026-07-29; v21.0 is the oldest still alive, until 2027-01-21) ([changelog](https://developers.facebook.com/docs/graph-api/changelog)). Everything below was checked against the live docs today unless flagged "secondary source" or "unverified".

Three things changed in 2025–2026 that invalidate most older write-ups:
1. **Embedded Signup v4** is the current version; v2/v3 were deprecated **2026-10-15** (already past). ([ES overview](https://developers.facebook.com/docs/whatsapp/embedded-signup), [v4](https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/version-4.md))
2. **New account model**: the WABA is being split into a *WhatsApp account (WAAC)* (phone number, profile) and a *Messaging account* (templates, billing, webhooks). GA rollout started 2026-09-23, all businesses by mid-Oct 2026. Existing `waba_id` values now mean "Messaging account ID". Phone number migration between partners no longer exists; customers *share* the number with a second partner instead. ([account model](https://developers.facebook.com/documentation/business-messaging/whatsapp/account-model-evolution.md))
3. **Pricing**: per-message pricing since 2025-07-01; and as of **2026-10-01** service (free-form) messages are billed beyond 1,000 free/month per phone number, and utility templates inside the 24h window are no longer free. ([pricing](https://developers.facebook.com/documentation/business-messaging/whatsapp/pricing.md))

## A. Onboarding model for a multi-tenant SaaS

### A1. Tech Provider vs Solution Partner vs Tech Partner
Source: [Solution providers overview](https://developers.facebook.com/docs/whatsapp/solution-providers), [Tech Provider get-started](https://developers.facebook.com/docs/whatsapp/solution-providers/get-started-for-tech-providers).

| | Solution Partner (BSP) | Tech Provider | Tech Partner |
|---|---|---|---|
| Meta Business Partner | Yes ("lengthy process") | No | Tech Provider that became an MBP |
| Credit line with Meta, extendable to clients | Yes (must share it during onboarding) | No | No |
| Who pays Meta for messages | Partner (invoices clients) | **The client's own Messaging account** (client adds a card in WhatsApp Manager) | Client |
| Onboards other businesses via Embedded Signup | Yes | **Yes** | Yes |
| Direct Support | Yes | Yes | Yes |

- **Hay should be a Tech Provider.** It is self-service: App Dashboard → Use cases → Customize (WhatsApp) → "Tech Provider onboarding". Steps: (1) verify *your own* business portfolio (Business Verification is a prerequisite for App Review); (2) App Review for Advanced Access to `whatsapp_business_messaging` + `whatsapp_business_management` (two screen-recordings: sending a message from your app, creating a template from your app); (3) optionally pair with a Solution Partner ("Multi-Partner Solution") if you want their credit line to cover clients. No timeline is published; Business Verification is usually days, App Review days-to-weeks (not stated officially).
- **Access Verification is no longer required** to become a Tech Provider (changelog 2025-10-03) ([changelog](https://developers.facebook.com/documentation/business-messaging/whatsapp/changelog.md)). The ES overview page still lists it as one of the three things that raise your onboarding cap; treat it as legacy wording.
- **Onboarding cap**: default **10 new business customers per rolling 7 days**; after Business Verification + App Review (+ Access Verification per the page) it rises to **200/7 days**. More than that requires Meta Business Partner status. Count visible in WhatsApp Manager → Partner overview. ([ES overview](https://developers.facebook.com/docs/whatsapp/embedded-signup))
- Tech Providers use **business tokens** (business-integration system-user tokens) exclusively; Solution Partners additionally use their own system-user token (with `business_management`, Admin/Finance-editor role) to share the credit line. ([access tokens](https://developers.facebook.com/documentation/business-messaging/whatsapp/access-tokens.md))
- `business_management` permission is **not** needed for a pure Tech Provider flow (only the two WhatsApp permissions); it is needed if you use the Credit Allocation API or the `system_user_access_tokens` endpoint (Hosted ES path).

### A2. Embedded Signup v4 — exact flow
Sources: [implementation](https://developers.facebook.com/docs/whatsapp/embedded-signup/implementation), [default flow](https://developers.facebook.com/docs/whatsapp/embedded-signup/default-flow), [v4](https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/version-4.md), [Facebook Login for Business](https://developers.facebook.com/docs/facebook-login/facebook-login-for-business).

**Setup**
- Business-type app with the WhatsApp use case + Facebook Login for Business product.
- App Dashboard → Facebook Login for Business → Configurations → create → login variation **"Embedded Signup"** → select products (Cloud API; optionally Marketing Messages API, CTWA, Conversions API…). Selecting products automatically puts you on **v4** and auto-adds the permissions. Upgrading to v4 *requires a new configuration*. Copy the `config_id`.
- Required assets/permissions for Cloud API: WhatsApp account (WAAC) + Messaging account; `whatsapp_business_management`, `whatsapp_business_messaging`.
- Client-side: FB JS SDK, `FB.init({appId, autoLogAppEvents:true, xfbml:true, version:'v26.0'})`.

**Launch (v4)**
```js
FB.login(fbLoginCallback, {
  config_id: '<CONFIG_ID>',
  response_type: 'code',
  override_default_response_type: true,
  extras: { setup: {} }        // v4: no featureType / sessionInfoVersion / version needed
});
```
- Do **not** pass `scope`.
- Pre-v5 coexistence flag was `extras.featureType = 'whatsapp_business_app_onboarding'` (+ `sessionInfoVersion: '3'`); in v4 default flow the coexistence branch is entered automatically when the number is already on the WhatsApp Business app, and in the upcoming v5 it is on by default with an opt-out `features: [{name:'whatsapp_business_app_onboarding', enabled:false}]`. ([coexistence](https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/onboarding-business-app-users.md)). Secondary sources report that legacy feature types `only_waba_sharing`, `marketing_messages_lite`, `coex` are not auto-migrated and fall back to the standard flow ([360dialog](https://360dialog.com/blog/embedded-signup-versions-migration/)).

**Message event (window `message` listener, origin must end with `facebook.com`)**
```json
{ "type": "WA_EMBEDDED_SIGNUP",
  "event": "FINISH",            // or FINISH_ONLY_WABA | FINISH_WHATSAPP_BUSINESS_APP_ONBOARDING | FINISH_OBO_MIGRATION | FINISH_GRANT_ONLY_API_ACCESS | CANCEL | ERROR
  "data": { "phone_number_id": "...", "waba_id": "...", "business_id": "...",
            "waba_ids": [...], "ad_account_ids": [...], "page_ids": [...] } }
```
- `CANCEL` carries `data.current_step`; errors carry `error_message`, `error_code`, `session_id`, `timestamp`. Closing the popup on the final screen counts as success.
- `waba_id` is now the **Messaging account ID**; `waac_id` will only be added in Phase 2 (H1 2027).
- The `FB.login` callback receives `response.authResponse.code` — an exchangeable **code with a 30-second TTL**. Ship it to your server immediately.
- You must also subscribe to the `account_update` webhook: `PARTNER_ADDED` / `PARTNER_APP_INSTALLED` fire when the customer finishes and carry `waba_info.waba_id`, `waba_info.owner_business_id`, `waba_info.partner_app_id` ([account_update ref](https://developers.facebook.com/documentation/business-messaging/whatsapp/webhooks/reference/account_update.md)). Use it as the source of truth / reconciliation if the browser event is lost.

**v4 UX**: "Phone Number First" — customer authenticates → authorizes → enters & verifies the number (SMS/voice) → selects/creates portfolio + WhatsApp account + Messaging account → permission summary → Finish. Rollout is still in progress so some customers see the old order. Customer can also claim up to two Meta "555" test numbers (display-name approval required before messaging). Customers created a WABA via a *developer app* cannot be onboarded through ES.

**Server-side steps after signup (Tech Provider)** — [onboarding as Tech Provider](https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/onboarding-customers-as-a-tech-provider.md):
1. Exchange code → business token: `GET https://graph.facebook.com/v26.0/oauth/access_token?client_id=<APP_ID>&client_secret=<APP_SECRET>&code=<CODE>` (no `redirect_uri`). Returns `{ "access_token": "...", "token_type": "bearer" }` — a **Business Integration System User access token** scoped to that customer's assets.
2. Subscribe your app to the customer's Messaging-account webhooks: `POST /<WABA_ID>/subscribed_apps` with `Authorization: Bearer <BUSINESS_TOKEN>` → `{"success":true}`. Optional body `{"override_callback_uri": "...", "verify_token": "..."}` to route this tenant's webhooks to a tenant-specific URL (≤200 chars) ([overrides](https://developers.facebook.com/docs/whatsapp/cloud-api/webhooks/override)).
3. Register the number: `POST /<PHONE_NUMBER_ID>/register` body `{"messaging_product":"whatsapp","pin":"123456"}` (6-digit; becomes the 2-step PIN or must match the existing one). **Skip for coexistence numbers** (already registered). Limited to 10 register/deregister per number per 72h (error 133016). ([registration](https://developers.facebook.com/docs/whatsapp/cloud-api/reference/registration))
4. (Optional) enable calling per number.
5. **Customer adds a payment method** in WhatsApp Manager → Overview → "Add payment method". For Tech Providers there is no credit line; Meta bills the customer's Messaging account directly. Until a payment method exists the customer can only use the free allowances; from 2026-10-01 Meta stops delivering service messages past the free tier without a payment method (deadline was 2026-09-30) ([non-template pricing](https://developers.facebook.com/documentation/business-messaging/whatsapp/pricing/non-template-messages.md)). Check `GET /<WABA_ID>?fields=primary_funding_id` — absent means no payment method ([messaging accounts](https://developers.facebook.com/documentation/business-messaging/whatsapp/account-model-evolution/messaging.md)).
6. Verify readiness with `GET /<PHONE_NUMBER_ID>?fields=health_status` (`can_send_message`: AVAILABLE/LIMITED/BLOCKED with per-entity errors) ([health status](https://developers.facebook.com/documentation/business-messaging/whatsapp/support/health-status.md)).

**Hosted Embedded Signup** (Oct 2025): Meta-hosted "zero integration" link you copy from WhatsApp → Quickstart → View onboarding. Cloud API only, not customizable. You learn of completion via `account_update: PARTNER_ADDED`, then fetch the customer's business token with `POST /<CUSTOMER_BUSINESS_PORTFOLIO_ID>/system_user_access_tokens` (`appsecret_proof` = HMAC-SHA256(system_token, app_secret), `fetch_only=true`, Bearer = your system token with `business_management`). Useful fallback / token re-fetch path even if you embed the JS flow. ([hosted ES](https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/hosted-es.md))

### A3. Permissions, App Review, verification
- `whatsapp_business_messaging` (send/receive, phone-number settings, `messages`/`calls` webhooks) and `whatsapp_business_management` (WABA settings, templates, all other webhooks) — both need **Advanced Access**; without `whatsapp_business_management` calls on assets your business doesn't own fail with code 200. ([set up webhooks](https://developers.facebook.com/docs/whatsapp/cloud-api/guides/set-up-webhooks), [TP get-started](https://developers.facebook.com/docs/whatsapp/solution-providers/get-started-for-tech-providers))
- Your (Hay's) business portfolio must pass **Business Verification** before App Review. Customers' portfolios do *not* need verification to onboard; verification is one of the paths from the 250 → 2,000 messaging tier and unlocks 20 numbers (vs 2) and OBA eligibility ([messaging limits](https://developers.facebook.com/docs/whatsapp/messaging-limits), [phone numbers](https://developers.facebook.com/docs/whatsapp/cloud-api/phone-numbers)).

### A4. Coexistence (WhatsApp Business app + Cloud API on the same number)
Source: [onboarding business app users](https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/onboarding-business-app-users.md), changelog.
- Requirements: WhatsApp Business app ≥ **2.24.17**; customer keeps the number in the app; you use ES. Flow: profile review → portfolio select/create → **QR scan from the Business app** → confirm business info (time zone required) → terms → success. Event `FINISH_WHATSAPP_BUSINESS_APP_ONBOARDING`. The existing business account is converted into a Messaging account with the same ID returned in `waba_id`; **no partner-specific Messaging account** is created.
- Availability expanded Oct 2025 to Australia, Japan, Philippines, Russia, South Korea, Turkey, EEA/EU, UK; Nigeria and South Africa added April 2026 (changelog). Assume broadly available now; the number's country code decides.
- Post-signup: do NOT call `/register`. Verify with `GET /<PHONE_NUMBER_ID>?fields=is_on_biz_app,platform_type` → `true` / `CLOUD_API`. Subscribe to `account_update`, `history`, `smb_app_state_sync`, `smb_message_echoes`. Within **24 hours** trigger syncs: `POST /<PHONE_NUMBER_ID>/smb_app_data {"messaging_product":"whatsapp","sync_type":"smb_app_state_sync"}` (contacts) and `{"sync_type":"history"}` (chat history). Each sync can run once; keep `request_id`. History declined → error `2593109`.
- History: last **180 days (6 months)**, delivered in phases (0–1 day, 1–90, 90–180), chunks with `chunk_order` and `progress` (100 = done); no group chats; media IDs only for last 14 days. Messages the owner sends from the phone arrive as `smb_message_echoes`; edit/revoke webhooks supported since Nov 2025.
- Limitations: fixed **20 mps** throughput; no groups, disappearing/view-once, live location, broadcast lists, voice/video calls, business tools/Channels in the app; up to 4 linked devices but all are unlinked at onboarding; Windows/WearOS clients unsupported. Only Cloud API messages open/affect the 24h window and pricing; app-sent messages stay free. First inbound from a user may surface error **131060** ("message currently unavailable"). Cannot `/deregister` a coexistence number. Disconnect from app Settings → Account → Business Platform → Disconnect triggers `account_update: PARTNER_REMOVED` with `disconnection_info`.
- Calling API requires Cloud-API-only numbers (not coexistence). OBA isn't granted to WhatsApp Business app numbers.

### A5. Migrating a number from Twilio to Hay
Official position under the **new account model**: *"Phone number migration isn't supported for accounts on the new WhatsApp account model"*; disconnecting the number from the current account doesn't free it. Instead the customer **shares the WhatsApp account (WAAC) that owns the number** with your app via Embedded Signup (Phase 1 explicitly supports "a client already onboarded with one partner onboarding with a different partner using their existing phone number"). ([migrate programmatically](https://developers.facebook.com/documentation/business-messaging/whatsapp/solution-providers/support/migrating-phone-numbers-among-solution-partners-programmatically.md), [account model onboarding](https://developers.facebook.com/documentation/business-messaging/whatsapp/account-model-evolution/onboarding.md))
- Consequences: no downtime at Meta's level; the number keeps display name, quality, messaging limit, OBA (they belong to the WAAC). Hay gets its *own* Messaging account on that number: **templates do not carry over** (templates belong to the Messaging account; "migrated templates reset quality rating and tier, ramp-up ~2–4 weeks"); billing is per Messaging account, so the customer must add a payment method on Hay's Messaging account even though Twilio's credit line covered the old one. Throughput and the per-portfolio messaging limit are *shared* across all partners on the number. Inbound webhooks: each partner's app receives delivery receipts for its own sends; the docs do not yet state inbound-message fan-out rules for multi-partner numbers — test this before promising customers they can run Twilio and Hay in parallel.
- Registration: re-registering a shared number "succeeds without resetting the PIN"; keep sending a valid 6-digit `pin`. The 2FA PIN is being deprecated for eligible numbers in Phase 1.
- Customer removes Twilio afterwards in Meta Business Suite by unsharing Twilio's Messaging account, then the WhatsApp account (optional; sharing is additive).
- **Legacy model (still applies to accounts not yet migrated — mid-Oct 2026 cutover was the plan)**: customer disables two-step verification in WhatsApp Manager (or asks Twilio), new BSP calls `POST /<DEST_WABA_ID>/phone_numbers` with `migrate_phone_number=true`, `country_code`, `phone_number`, then `request_code`/`verify_code`, then `/register`. Display name, messaging tier, quality rating and OBA status carry over; only high-quality approved templates are duplicated (quality shows UNKNOWN for 24h; some may be REJECTED); chat history does not move; source and destination must share the same data-localization region; billing cuts over at the moment of migration (secondary sources: [Twilio](https://www.twilio.com/docs/whatsapp/migrate-numbers-and-senders), [Bird](https://docs.bird.com/connectivity-platform/account/migrating-to-another-provider-bsp), [businesschat](https://help.businesschat.io/en/articles/6517849-how-to-migrate-a-phone-number-from-one-bsp-to-another)). Downtime is seconds-to-minutes around `verify_code`. If you hit "Phone number migration isn't supported", the account is already on the new model — use sharing.

## B. Messaging API (Graph API v26.0)

### B1. Webhooks
- Verification handshake: Meta `GET`s your URL with `hub.mode=subscribe&hub.verify_token=...&hub.challenge=...`; compare the token and echo `hub.challenge` as plain text with 200. ([Graph webhooks getting started](https://developers.facebook.com/docs/graph-api/webhooks/getting-started))
- Every POST carries `X-Hub-Signature-256: sha256=<hex HMAC-SHA256(raw body, app_secret)>`. Compute over the **raw bytes** (don't re-serialize). Optional mTLS: Meta presents a client cert, CN `client.webhooks.fbclientcerts.com`, CA `meta-outbound-api-ca-2025-12.pem` (DigiCert chain expired 2026-04-15).
- Respond 200 fast; WhatsApp retries non-200 with decreasing frequency for **up to 7 days** (generic Graph says 36h; WhatsApp page says 7 days) and may deliver duplicates to all subscribed apps — **be idempotent on `messages[].id` / `statuses[].id`**. Payloads up to 3 MB. ([set up webhooks](https://developers.facebook.com/docs/whatsapp/cloud-api/guides/set-up-webhooks))
- Subscribe fields in App Dashboard, then per tenant `POST /<WABA_ID>/subscribed_apps`. Per-tenant/per-number callback overrides are possible for `messages`, `calls`, `smb_*`, `history`, groups etc. — but **not** for `account_update`, `account_alerts`, `account_review_update`, template webhooks (those always hit the app default URL). Precedence: phone number override → WABA override → app URL. ([overrides](https://developers.facebook.com/docs/whatsapp/cloud-api/webhooks/override))

**Envelope**
```json
{"object":"whatsapp_business_account","entry":[{"id":"<WABA_ID>","changes":[{"field":"messages","value":{
  "messaging_product":"whatsapp",
  "metadata":{"display_phone_number":"15550783881","phone_number_id":"<PHONE_NUMBER_ID>"},
  "contacts":[{"profile":{"name":"Ana"},"wa_id":"5511999999999","user_id":"BR.1349120865530274","identity_key_hash":"..."}],
  "messages":[{"from":"5511999999999","from_user_id":"BR.1349...","id":"wamid.HBg...","timestamp":"1760000000","type":"text","text":{"body":"Hi"}}]
}}]}]}
```
Route by `metadata.phone_number_id` (tenant) — `entry.id` is the Messaging account. `from` and `wa_id` can differ; **`from`/`wa_id` may be absent** for users who adopted usernames — key customers by `contacts[].user_id` (BSUID, see C). ([BSUID](https://developers.facebook.com/documentation/business-messaging/whatsapp/business-scoped-user-ids.md))

**Inbound message types** (`messages[].type` → object) — [refs under webhooks/reference/messages/*](https://developers.facebook.com/documentation/business-messaging/whatsapp/webhooks/reference/messages/image.md):
- `text`: `text.body`.
- `image` / `video` / `sticker`: `{id, mime_type, sha256, caption?, url?}` (`sticker` has `animated`). `url` is rolling out since 2025-11-12 — do not depend on it.
- `audio`: `{id, mime_type ("audio/ogg; codecs=opus"), sha256, voice: true|false, url?}`.
- `document`: `{id, mime_type, sha256, filename, caption?, url?}`.
- `location`: `{latitude, longitude, name?, address?, url?}`.
- `contacts`: array of vCards: `name{formatted_name,first_name,last_name,...}`, `phones[]{phone, wa_id, type}`, `emails[]`, `addresses[]`, `org{}`, `urls[]`, `birthday`.
- `interactive`: `interactive.type` = `button_reply` `{id,title}` | `list_reply` `{id,title,description}` | `nfm_reply` (Flows) `{name:"flow", body:"Sent", response_json:"<string>"}`; plus `context.{from,id}` pointing at your original message. ([interactive ref](https://developers.facebook.com/documentation/business-messaging/whatsapp/webhooks/reference/messages/interactive.md), [flows webhooks](https://developers.facebook.com/documentation/business-messaging/whatsapp/flows/guides/flowswebhooks.md))
- `button` (template quick-reply tap): `button.payload`, `button.text`, `context.id`.
- `reaction`: `reaction.message_id`, `reaction.emoji` (**absent = reaction removed**); only for your messages ≤30 days old.
- `order`: `order.catalog_id`, `order.text`, `order.product_items[]{product_retailer_id, quantity, item_price, currency}`.
- `system`: e.g. `user_changed_number`, `user_changed_user_id` (`user_id`, `previous_user_id`).
- `request_welcome`: user opened a chat from an ad/CTA (no text yet) — treat as a "hello" trigger.
- `unsupported`: `errors[]` with 131051 (unknown type: polls, edits, pins, group invites, gifs, etc. — `unsupported.type` tells you which) or 131060 (coexistence first contact).
- Common optional objects on any inbound: `context` (`from`, `id` = replied-to wamid; `forwarded`, `frequently_forwarded`; `referred_product{catalog_id, product_retailer_id}`) and `referral` for Click-to-WhatsApp ads: `{source_url, source_id, source_type:"ad", headline, body, media_type, image_url|video_url+thumbnail_url, ctwa_clid, welcome_message.text}` (`ctwa_clid` omitted for Status placements). ([text ref](https://developers.facebook.com/documentation/business-messaging/whatsapp/webhooks/reference/messages/text.md))

**Statuses** (`value.statuses[]`) — [status ref](https://developers.facebook.com/documentation/business-messaging/whatsapp/webhooks/reference/messages/status.md):
```json
{"id":"wamid...","status":"sent|delivered|read|played|failed","timestamp":"...","recipient_id":"5511...","recipient_user_id":"BR....",
 "biz_opaque_callback_data":"<your string>",
 "conversation":{"id":"...","expiration_timestamp":"...","origin":{"type":"service|utility|marketing|marketing_lite|authentication|authentication_international|referral_conversion"}},
 "pricing":{"billable":true,"pricing_model":"PMP","type":"regular|free_customer_service|free_entry_point","category":"service|utility|marketing|authentication|authentication-international|referral_conversion|marketing_lite|group_*|general_purpose_ai"},
 "errors":[{"code":131047,"title":"...","message":"...","error_data":{"details":"..."},"href":"..."}]}
```
- `played` added Nov 2025 for voice notes. Since v24.0 the `conversation` object is **omitted unless the message is inside a free-entry-point window**; `pricing.billable` is being deprecated in favour of `pricing.type` + `category`. `pricing_model` is `PMP` (per-message); `CBP` only on pre-July-2025 webhooks.
- `value.errors[]` (same shape) carries system/app/account-level errors.

### B2. Sending — `POST /<PHONE_NUMBER_ID>/messages`, Bearer business token
[send messages](https://developers.facebook.com/docs/whatsapp/cloud-api/guides/send-messages). Common: `messaging_product:"whatsapp"`, `recipient_type:"individual"|"group"`, `to:"+5511..."` (**include `+`/country code**; without it Meta prepends the business's country code) or `recipient:"<BSUID>"` (July 2026+; `to` wins if both). Optional `context:{message_id}` to quote (no bubble if the original is >30 days old, or when replying with a template; reactions can't be contextual) ([contextual replies](https://developers.facebook.com/documentation/business-messaging/whatsapp/messages/contextual-replies.md)), `biz_opaque_callback_data` (echoed in statuses), and `messaging_account_id` (only when your token can reach >1 Messaging account on the number — optional now, required on newest version H1 2027, all versions H1 2028; `paid_messaging_account_id` alias dies 2026-12-31). Response: `{contacts:[{input, wa_id, user_id}], messages:[{id, message_status?}]}` — success = accepted, not delivered.
- `text`: `{"type":"text","text":{"body":"≤4096 chars","preview_url":true}}`.
- Media: `{"type":"image","image":{"id":"<MEDIA_ID>"|"link":"https://...","caption":"≤1024"}}`; same for `audio` (no caption), `video`, `document` (+`filename`), `sticker`. Upload first: `POST /<PHONE_NUMBER_ID>/media` multipart `file`, `type=<mime>`, `messaging_product=whatsapp` → `{id}`. Link-based media is cached by Meta for 10 min; append a random query to bust. ([media](https://developers.facebook.com/docs/whatsapp/cloud-api/reference/media), [image messages](https://developers.facebook.com/documentation/business-messaging/whatsapp/messages/image-messages.md))
- `reaction`: `{"type":"reaction","reaction":{"message_id":"wamid...","emoji":"👍"}}` (empty string removes — longstanding behaviour, not restated on the current page); target ≤30 days old, must be a user message; only a `sent` status is emitted. ([reactions](https://developers.facebook.com/documentation/business-messaging/whatsapp/messages/reaction-messages.md))
- `location`: `{"type":"location","location":{"latitude","longitude","name","address"}}`; `contacts`: `{"type":"contacts","contacts":[{...vCard}]}`; `interactive.type:"location_request_message"` asks the user to share location.
- Interactive reply buttons: `{"type":"interactive","interactive":{"type":"button","header":{type:text|image|video|document},"body":{"text":"≤1024"},"footer":{"text":"≤60"},"action":{"buttons":[{"type":"reply","reply":{"id":"≤256","title":"≤20"}}]}}}` — max **3** buttons. ([reply buttons](https://developers.facebook.com/documentation/business-messaging/whatsapp/messages/interactive-reply-buttons-messages.md))
- Interactive list: `interactive.type:"list"`, `action.button` (≤20), `action.sections[1..10]{title ≤24, rows[]{id ≤200, title ≤24, description ≤72}}` — **≤10 rows total**, header text-only ≤60, body ≤4096. ([lists](https://developers.facebook.com/documentation/business-messaging/whatsapp/messages/interactive-list-messages.md))
- CTA URL: `interactive.type:"cta_url"`, `action.name:"cta_url"`, `action.parameters{display_text,url}`. Voice-call button and media carousel also exist.
- Flows: `interactive.type:"flow"`, `action.name:"flow"`, `action.parameters{flow_message_version:"3", flow_id|flow_name, flow_cta (≤30), flow_token, mode:"published"|"draft", flow_action:"navigate"|"data_exchange", flow_action_payload{screen,data}}`. Reply arrives as `nfm_reply.response_json` (put an identifier in `flow_token`; flow id is not echoed). Endpoint-backed flows require RSA/AES encryption on your endpoint. ([sending a flow](https://developers.facebook.com/documentation/business-messaging/whatsapp/flows/guides/sendingaflow.md))
- Mark as read + typing indicator (added April 2025): `{"messaging_product":"whatsapp","status":"read","message_id":"<inbound wamid>","typing_indicator":{"type":"text"}}` → `{"success":true}`. Indicator clears when you send or after **25 s**. Only send when you will actually reply. ([typing indicators](https://developers.facebook.com/docs/whatsapp/cloud-api/typing-indicators))
- Templates: `{"type":"template","template":{"name":"order_confirmation","language":{"code":"en_US"},"components":[{"type":"header","parameters":[{"type":"image","image":{"id":"..."}}]},{"type":"body","parameters":[{"type":"text","parameter_name":"first_name","text":"Jessica"}]},{"type":"button","sub_type":"quick_reply|url|copy_code|flow","index":"0","parameters":[{"type":"payload","payload":"..."}]}]}}`. Positional (`{{1}}`) is the default; named params need `parameter_name`. Response may include `message_status: "accepted" | "held_for_quality_assessment"` when the template is paced. ([template overview](https://developers.facebook.com/documentation/business-messaging/whatsapp/templates/overview.md), [pacing](https://developers.facebook.com/documentation/business-messaging/whatsapp/templates/template-pacing.md))
- Groups API (Oct 2025) exists (`recipient_type:"group"`, group webhooks) — not needed for support.

**Throughput & rate limits** ([overview](https://developers.facebook.com/docs/whatsapp/cloud-api/overview), [throughput](https://developers.facebook.com/documentation/business-messaging/whatsapp/throughput.md)):
- **80 mps per phone number** default (inbound+outbound all count); auto-upgrade to up to 1,000 mps requires unlimited tier + 100K uniques/24h + quality ≥ YELLOW (one-minute blip with 131057 during upgrade). Coexistence numbers fixed at 20 mps. Read with `GET /<PHONE_NUMBER_ID>?fields=throughput`.
- Pair rate limit: 1 message / 6 s to the same user (~600/h), bursts up to 45 in 6 s borrow from future quota → **131056**. 130429 = throughput hit. Backoff guidance 4^x seconds.
- Business Management API: 200 req/h per app per WABA (5,000/h once a number is registered).

**Media download**: `GET /<MEDIA_ID>[?phone_number_id=...]` → `{url, mime_type, sha256, file_size, id, messaging_product}`; then `GET <url>` with the same Bearer token (curl-style; browsers won't). URL expires in **5 minutes** (re-GET for a fresh one). Media persists 30 days; media IDs from webhooks expire after **7 days**, IDs you uploaded after 30 days. Sizes: image 5 MB (JPEG/PNG, 8-bit RGB/RGBA), video 16 MB (MP4/3GPP, H.264+AAC), audio 16 MB (AAC/AMR/MP3/M4A/OGG-opus mono), document 100 MB, sticker 100 KB static / 500 KB animated WebP. Under "No Storage" mode inbound media lives 1 h. ([media](https://developers.facebook.com/docs/whatsapp/cloud-api/reference/media), [no storage](https://developers.facebook.com/documentation/business-messaging/whatsapp/no-storage.md))

### B3. Windows, templates, categories
- **24-hour customer service window** opens/resets on each user message *or call*; inside it any message type; outside only approved templates. Error **131047** if you try free-form outside. Only Cloud-API traffic (not Business-app traffic) counts for coexistence numbers.
- **Free entry point window**: user messages via a Click-to-WhatsApp ad (Android/iOS) and you reply within the 24h window → window "may remain open for up to **7 days**" (the old 72h figure is gone from the official page; third parties still quote 72h) and marketing/utility/auth/service messages in it are free (`pricing.type: free_entry_point`). Facebook Page CTA buttons are no longer mentioned on the pricing page. ([pricing](https://developers.facebook.com/documentation/business-messaging/whatsapp/pricing.md))
- Template categories: **marketing, utility, authentication** (service is a *pricing* category for non-template replies, not a template category). Meta validates the category at creation (reject reason `INCORRECT_CATEGORY`), auto-recategorizes later (`template_category_update` webhook with `previous_category/new_category/correct_category`; `allow_category_change` is obsolete since 2025-04-09), and escalates utility-abuse via `account_update` events `UTILITY_TEMPLATE_ABUSE_RATE_LIMIT` / `RESTRICTED_UTILITY_TEMPLATES`; error **131064** = limited for template-classification violations. ([categorization](https://developers.facebook.com/documentation/business-messaging/whatsapp/templates/template-categorization.md))
- Management API ([template management](https://developers.facebook.com/documentation/business-messaging/whatsapp/templates/template-management.md)): `POST /<WABA_ID>/message_templates {name, language, category, parameter_format, components[]}` (media headers need a Resumable Upload `header_handle`), `GET /<WABA_ID>/message_templates?fields=name,status,category,quality_score&status=APPROVED`, `POST /<TEMPLATE_ID>` to edit (10 edits/30 days, 1/24h for approved; category of approved templates can't change), `DELETE /<WABA_ID>/message_templates?name=` or `hsm_id=`, `POST /<TEMPLATE_ID>/unpause`. Review usually automatic, up to 24h. Status: `PENDING, APPROVED, REJECTED, PAUSED, DISABLED, PENDING_DELETION, IN_APPEAL, ARCHIVED…`. Limits: 250 templates per Messaging account (6,000 if the portfolio is verified and a number has an approved display name), 100 creations/h; names lowercase/underscore ≤512, 30-day name quarantine after delete; inactive 12 months → archived → deleted after 28 days. Templates are **per Messaging account** — each tenant creates their own under their WABA; they do not transfer when a customer switches partners.
- Quality/pausing: template `quality_score` GREEN/YELLOW/RED/UNKNOWN; RED → paused 3h, then 6h, then DISABLED; pacing holds a slice of a marketing campaign for feedback (`held_for_quality_assessment`; dropped messages fail with 132015). `message_template_status_update` webhook carries `event` (APPROVED, REJECTED, PAUSED, DISABLED, FLAGGED, REINSTATED, PENDING_DELETION, ARCHIVED, LIMIT_EXCEEDED…), `reason`, `other_info.title` (FIRST_PAUSE/SECOND_PAUSE/…), `rejection_info`. ([pausing](https://developers.facebook.com/documentation/business-messaging/whatsapp/templates/template-pausing.md), [status webhook](https://developers.facebook.com/documentation/business-messaging/whatsapp/webhooks/reference/message_template_status_update.md))

### B4. Pricing (2026)
Sources: [pricing](https://developers.facebook.com/documentation/business-messaging/whatsapp/pricing.md), [non-template](https://developers.facebook.com/documentation/business-messaging/whatsapp/pricing/non-template-messages.md), [AI providers](https://developers.facebook.com/documentation/business-messaging/whatsapp/pricing/ai-providers.md).
- Per-message since **2025-07-01** (`pricing_model: PMP`); charged on **delivery**, by category × recipient market (country calling code). Inbound is free.
- Categories: marketing, utility, authentication (+ authentication-international in 18 markets), **service** (any non-template reply from a human or third-party AI inside the 24h window), and **Meta Business Agent** (Meta's own AI replies, $2.00 per 1M tokens ≈ 4–5¢/message, billed from 2026-08-01).
- **Service messages**: free since 2024-11-01 → **billed again from 2026-10-01** beyond **1,000 free delivered service messages per business phone number per month** (no rollover; govt/non-profit exempt until 2027-12-31). Service rates equal the market's utility rate; no volume tiers. Businesses without a payment method on file by 2026-09-30 have service delivery stopped once the free tier is exhausted.
- **Utility inside the 24h window**: free from 2025-07-01 → **billed from 2026-10-01**.
- Volume tiers apply only to utility and authentication, aggregated per portfolio per market, reset monthly (`account_update: VOLUME_BASED_PRICING_TIER_UPDATE`). Rate card changed 40 rates on 2026-10-01; Marketing Messages API has a "max price per message" option.
- **Who is billed**: the **Messaging account that sent the message** (its own payment method / spend limits / currency chosen at creation; 16 currencies; BRL localization deadline 2027-06-30, INR 2026-12-31). For a Tech Provider that is the customer's card; a Solution Partner's credit line only covers messages sent through the partner's Messaging account. Hay should expect to model "Meta bills you directly" in its own pricing and onboarding copy.
- AI Providers (general-purpose assistants) have a special per-message rate where they are legally allowed (Brazil from 2026-03-11; EU markets charged 2026-03-11→05-12 then free after the Commission's interim order; Türkiye free until at least 2027-04-11); webhook `pricing.category: general_purpose_ai`. This does **not** change pricing for ordinary businesses.

### B5. Messaging limits, quality, OBA
- Limits are **per business portfolio** since 2025-10-07 (shared by all numbers): **250 → 2,000 → 10,000 → 100,000 → unlimited** unique users / rolling 24h *outside* service windows (there is no 1K tier anymore). To 2,000: Business Verification, or partner-led verification, or 2,000 delivered template messages to unique users in 30 days with good quality (then Meta reviews). Above: automatic within 6h when quality is high and ≥50 % of the limit was used in 7 days. Read `whatsapp_business_manager_messaging_limit` (returns `TIER_250` …) on portfolio/WABA/number; `messaging_limit_tier` is deprecated. Webhooks: `business_capability_update` (`max_daily_conversations_per_business`, v24+), `phone_number_quality_update` (`event: ONBOARDING | THROUGHPUT_UPGRADE`, `current_limit`/`old_limit` deprecated Feb 2026), `account_alerts` (`INCREASED_CAPABILITIES_ELIGIBILITY_DEFERRED/FAILED/NEED_MORE_INFO`, `OBA_APPROVED/REJECTED`, `PROFILE_PICTURE_LOST`). The old FLAGGED/RESTRICTED quality state that lowered limits was removed in Oct 2025; a quality drop no longer reduces the tier. ([messaging limits](https://developers.facebook.com/docs/whatsapp/messaging-limits), [upcoming changes](https://developers.facebook.com/documentation/business-messaging/whatsapp/upcoming-messaging-limits-changes.md), [account_alerts](https://developers.facebook.com/documentation/business-messaging/whatsapp/webhooks/reference/account_alerts.md))
- Number `quality_rating`: GREEN/YELLOW/RED/UNKNOWN/NA from blocks/reports over 7 days (secondary sources for the window).
- Policy enforcement: warning → 1/3-day template & add-number blocks → 5/7/30-day full blocks → indefinite lock → disable; appeal in Business Support Home, 24–48h. `account_update` events `ACCOUNT_VIOLATION`, `ACCOUNT_RESTRICTION` (`restriction_info{restriction_type, expiration}`), `DISABLED_UPDATE` (`ban_info`). ([policy enforcement](https://developers.facebook.com/documentation/business-messaging/whatsapp/policy-enforcement.md))
- **Official Business Account** (blue check): free, merit-based; requires policy compliance, ≥30 days on the platform, verified portfolio, 2-step verification on, approved display name; apply in WhatsApp Manager; `GET /<PHONE_NUMBER_ID>?fields=official_business_account` → `oba_status`. Not granted to test or Business-app numbers. Separately, "Meta Verified for business" is a paid subscription that also yields a blue badge (secondary sources). ([OBA](https://developers.facebook.com/documentation/business-messaging/whatsapp/official-business-accounts.md))

### B6. Phone-number requirements
[phone numbers](https://developers.facebook.com/docs/whatsapp/cloud-api/phone-numbers), [display names](https://developers.facebook.com/documentation/business-messaging/whatsapp/display-names.md), [phone numbers ref](https://developers.facebook.com/docs/whatsapp/cloud-api/reference/phone-numbers).
- Must be owned by the business, receive SMS or voice, not a short code; **cannot be active on the consumer WhatsApp app** (delete the account first) and if on the WhatsApp Business app must go through coexistence; banned numbers must be appealed first. Landline/VoIP/toll-free OK with voice OTP (allow international calls, no IVR in the way). New portfolios: 2 numbers; 20 after verification or reaching 2,000 tier.
- Verification: `POST /<PHONE_NUMBER_ID>/request_code {code_method: SMS|VOICE, language}` → `POST /<PHONE_NUMBER_ID>/verify_code {code}` (ES does this in-flow). `code_verification_status`.
- Display name required at registration; reviewed automatically when you cross a messaging tier; `name_status`: APPROVED, AVAILABLE_WITHOUT_REVIEW, PENDING_REVIEW, DECLINED, EXPIRED, NONE. Change via `POST /<PHONE_NUMBER_ID>?new_display_name=…` (10×/30 days) → wait for `phone_number_name_update` (`decision: APPROVED`) → **re-`/register` within 14 days** or the name doesn't take effect. Error 131037 = 555 test number without approved name.
- 2-step PIN can't be disabled via API (WhatsApp Manager emails a disable link); PIN change via the Phone Number API `pin` field; needed to delete the number. Being deprecated under the new model.
- Dev/test: Meta auto-creates a test WABA + test number on Get Started; relaxed limits, templates (`hello_world`) send without a payment method, but only to numbers on the recipient allow-list (third-party sources say 5 recipients — unverified); customers can't message it. ES customers can also claim up to two 555 numbers. The temporary App-Dashboard token "expires quickly" (~23–24h per third parties) — use a system-user token for dev. ([get started](https://developers.facebook.com/docs/whatsapp/cloud-api/get-started))
- Useful fields on `GET /<PHONE_NUMBER_ID>?fields=`: `display_phone_number, verified_name, name_status, new_name_status, code_verification_status, quality_rating, throughput, status (CONNECTED…), account_mode (SANDBOX|LIVE), platform_type, is_on_biz_app, last_onboarded_time, webhook_configuration, health_status, official_business_account, whatsapp_business_manager_messaging_limit`. List: `GET /<WABA_ID>/phone_numbers`.

## C. Accounts, tokens, security, policy

### C1. Tokens
[access tokens](https://developers.facebook.com/documentation/business-messaging/whatsapp/access-tokens.md), [FB Login for Business](https://developers.facebook.com/docs/facebook-login/facebook-login-for-business), [error codes](https://developers.facebook.com/docs/whatsapp/cloud-api/support/error-codes).
- **User access token**: short-lived (hours), dev/testing only.
- **System user token** (Hay's own portfolio): long-lived; expiry chosen at generation (60 days or never). Needed by Hay only for its own test assets, Hosted-ES token fetch, or credit-line APIs. Permissions: `business_management`, `whatsapp_business_management`, `whatsapp_business_messaging`.
- **Business Integration System User token ("business token")**: what ES returns; scoped to one customer's granted assets; **never expires by default** (the configuration can instead be set to 60-day expiry — the template is literally called "…Configuration With 60 Expiration Token"; pick *never* for a server-side integration). Not shareable across client businesses. Re-fetchable without the customer redoing ES via `POST /<CLIENT_BUSINESS_ID>/system_user_access_tokens` (`fetch_only=true`, `appsecret_proof`, Bearer = your system token w/ `business_management`); `GET /me?fields=client_business_id` with the business token gives that ID.
- Debug: `GET /debug_token?input_token=<TOKEN>` with an app token (`<APP_ID>|<APP_SECRET>`) → `data.{app_id, type:"SYSTEM_USER"…, expires_at:0, is_valid, scopes[], granular_scopes[]{scope, target_ids[]}}` — use it to confirm `whatsapp_business_messaging`/`management` cover the tenant's WABA (standard Graph API endpoint; the WhatsApp pages don't restate it).
- **Revocation**: customer removes your app in Business Settings → Integrations → Connected apps (or disconnects in the Business app) → token invalid → calls fail with **code 190** (expired/invalidated) or **0**/**10**/**200** (permission). You also receive `account_update: PARTNER_APP_UNINSTALLED` / `PARTNER_REMOVED` (`disconnection_info{reason, initiated_by}`), and under the new model `ACCOUNT_OFFBOARDED` / `ACCOUNT_RECONNECTED`. Handle these to mark the channel disconnected and prompt re-onboarding.
- Store tokens encrypted per tenant; never ship them to the browser; use `appsecret_proof` on server calls where supported.

### C2. WABA webhook fields Hay should subscribe to
[set up webhooks](https://developers.facebook.com/docs/whatsapp/business-management-api/guides/set-up-webhooks): `messages` (inbound + statuses; also system/BSUID change events), `account_update` (PARTNER_ADDED, PARTNER_APP_INSTALLED/UNINSTALLED, PARTNER_REMOVED, ACCOUNT_VIOLATION, ACCOUNT_RESTRICTION, DISABLED_UPDATE, ACCOUNT_DELETED, ACCOUNT_OFFBOARDED/RECONNECTED, VOLUME_BASED_PRICING_TIER_UPDATE, BUSINESS_PRIMARY_LOCATION_COUNTRY_UPDATE, AD_ACCOUNT_LINKED, AUTH_INTL_PRICE_ELIGIBILITY_UPDATE, MM_LITE_TERMS_SIGNED), `account_alerts`, `account_review_update`, `business_capability_update`, `phone_number_name_update`, `phone_number_quality_update`, `message_template_status_update`, `message_template_quality_update`, `message_template_components_update`, `template_category_update`, `security` (2FA changes), `user_preferences` (marketing opt-out), `business_username_updates`; for coexistence `history`, `smb_app_state_sync`, `smb_message_echoes`; `calls` if you do voice; `partner_solutions` only for Multi-Partner Solutions. (`messages`/`calls` need `whatsapp_business_messaging`; everything else `whatsapp_business_management`.)

### C3. Data, retention, GDPR/LGPD
- Standard Cloud API stores message content at rest for **up to 30 days** (for retransmission); phone numbers tied to messages go with them; undelivered webhooks are retried up to 7 days; outbound templates retried for their TTL (default 30 days). ([No Storage](https://developers.facebook.com/documentation/business-messaging/whatsapp/no-storage.md), secondary [360dialog](https://docs.360dialog.com/docs/waba-basics/architecture-and-security))
- **Local Storage** (data residency, at-rest only, in-use up to 60 min elsewhere): `data_localization_region` ∈ AU, ID, IN, JP, SG, KR, DE, CH, GB, BR, BH, ZA, AE, CA; set via `POST /<PHONE_NUMBER_ID>/settings {storage_configuration:{status:"IN_COUNTRY_STORAGE_ENABLED", data_localization_region:"BR"}}` before `/register` (v21+), or `/register` param on old versions; changing requires deregister/re-register (<5 min, no re-verification). Contact-book numbers aren't localized. ([local storage](https://developers.facebook.com/documentation/business-messaging/whatsapp/local-storage.md))
- **No Storage** (Dec 2025): `storage_configuration:{status:"NO_STORAGE_ENABLED", retention_minutes:60}` — nothing at rest, 1-hour in-transit; webhook retries drop to 1 h (missed inbound → error 131035), inbound media deleted after 1 h, outbound media TTL `ttl_minutes` 60–43200, decryption retries limited (131036). Good story for EU/LGPD-sensitive tenants but you must be highly available.
- Legal framing: WhatsApp Business Platform Terms (effective 2026-09-23) incorporate the Business Messaging Policy and Meta Terms for WhatsApp Business Platform; Meta acts as processor for Cloud API hosting under those terms (Meta's own DPA text was not retrievable via fetch — have legal pull it from Business Settings). Business data **may not be used to train or develop AI models** by third-party providers (secondary: [GoHighLevel summary](https://help.gohighlevel.com/support/solutions/articles/155000006792-updates-to-whatsapp-business-solution-terms)). Your opt-in and escalation obligations live in the [Business Messaging Policy](https://whatsappbusiness.com/policy/) (last updated 2026-09-23).

### C4. Newer capabilities worth knowing
- **Business-Scoped User IDs & usernames** (2026): BSUIDs (`US.13491208655302741918`) appear in `contacts[].user_id`, `messages[].from_user_id`, `statuses[].recipient_user_id` since April 2026; users who adopt a WhatsApp username (reservations from 2026-06-29) hide their phone number, so `from`/`wa_id` can be missing. Send with `recipient:"<BSUID>"` (July 2026+), request a number with the `request_contact_info` interactive button ("Share Contact Info"), handle `user_changed_number` / `user_changed_user_id` system messages, and update block/group calls to take `user_id`. BSUIDs are per business *portfolio*, so a BSUID from one tenant can't be used by another. Meta says support is "required for all partners". This directly affects Hay's `Customer.external_id` keying — key WhatsApp customers by BSUID with phone as an optional attribute. ([BSUID](https://developers.facebook.com/documentation/business-messaging/whatsapp/business-scoped-user-ids.md))
- **Calling API** (GA July 2025): user- and business-initiated VoIP via WebRTC or SIP; enable per number; needs the 2,000 tier; `calls` webhook; business-initiated calls need user permission and aren't available for US/CA/EG/VN/NG numbers; calls open the 24h window. ([calling](https://developers.facebook.com/documentation/business-messaging/whatsapp/calling.md))
- **Flows**: see B2; management via `/<WABA_ID>/flows`, Flow JSON, optional encrypted data-exchange endpoint. ([flows](https://developers.facebook.com/docs/whatsapp/flows))
- **Block API**: `POST|DELETE|GET /<PHONE_NUMBER_ID>/block_users {block_users:[{user:"+1650..."}]}` (≤1,000 per call, 64k list, only users who messaged in the last 24h). ([block users](https://developers.facebook.com/documentation/business-messaging/whatsapp/block-users.md))
- **Marketing Messages API** (ex "Lite"; GA 2026): send-only `/marketing_messages` endpoint with Meta-optimized delivery and max-price; requires MM terms; not needed for support.
- **Groups API** (Oct 2025), **Meta Business Agent / Business Agent Platform** (June 2026: Meta's own AI agent on WhatsApp, token-billed) — a competitor to Hay rather than an API you'd use.

### C5. The AI policy — what is actually banned (important)
- October 2025 Meta added an **"AI Providers"** section to the WhatsApp Business Solution Terms: *"Providers and developers of artificial intelligence or machine learning technologies, including but not limited to large language models, generative AI platforms, general-purpose AI assistants, or similar technologies, are strictly prohibited from accessing or using the WhatsApp Business Solution, whether directly or indirectly… where such technologies are the primary (rather than incidental or ancillary) functionality being made available for use, as determined by Meta in its sole discretion."* Applied to new sign-ups from 2025-10-15 and to everyone from **2026-01-15** (ChatGPT, Perplexity, Copilot left WhatsApp). ([TechCrunch](https://techcrunch.com/2025/10/18/whatssapp-changes-its-terms-to-bar-general-purpose-chatbots-from-its-platform), [Meta AI-providers pricing page](https://developers.facebook.com/documentation/business-messaging/whatsapp/pricing/ai-providers.md))
- Meta's stated carve-out: *"this move doesn't affect businesses that are using AI to serve customers on WhatsApp — e.g. a travel company running a bot for customer service."* Meta's own pricing page defines a service message as a non-template reply "from a person or from a **third-party AI solution**", i.e. third-party AI support bots are an explicitly contemplated, billable use. **A business-specific support agent that Hay runs on a merchant's own number, answering about that merchant's products/orders, is allowed.** What is banned is distributing an open-ended assistant *as the product* on a WhatsApp number (or letting a tenant's bot behave like one).
- Later developments: Meta introduced a paid "AI Provider" access tier in some markets in March 2026; the European Commission issued **interim measures on 2026-06-09** ordering Meta to restore pre-October-2025 (free) access for rival assistants in the EEA, and Meta stopped charging EU AI Providers from 2026-05-13; Brazil's regulator pushed similarly; Türkiye access from 2026-10-15. None of this changes the position for business support bots. ([Engadget](https://engadget.com/2191213/eu-orders-meta-to-stop-blocking-rival-ai-chatbots-on-whatsapp), AI-providers page above)
- Other obligations that *do* bind Hay's tenants (Business Messaging Policy, updated 2026-09-23): automation inside the 24h window is fine but the business "must also have available prompt, clear, and direct escalation paths" to a human (in-chat handoff, phone, email, web form — not just a help-center link); opt-in required for business-initiated messages (separate opt-ins per category and for calls recommended); honor opt-outs; no explicit "you are talking to an AI" disclosure rule in the policy text, though it's good practice and some jurisdictions (EU AI Act) require it. ([policy](https://whatsappbusiness.com/policy/))

## Gotchas / things most people get wrong
1. **ES v2/v3 died on 2026-10-15.** Build on v4 with a *new* FB-Login-for-Business configuration; drop `featureType`/`sessionInfoVersion`/`version` from `FB.login`.
2. The ES `code` lives **30 seconds** — exchange synchronously; don't queue it. Also persist `PARTNER_ADDED` webhooks as the reconciliation path.
3. **Adding the number in ES does not register it.** You must call `/register` with a PIN or every send fails with 133010. Except coexistence numbers (already registered) — check `is_on_biz_app`.
4. **The customer can't message until they add a card** (Tech Provider model). Surface `primary_funding_id`/`health_status` in the Hay UI and tell them Meta bills them directly, separately from Hay. From 2026-10-01 even replies cost money past 1,000/number/month.
5. `waba_id` is now a **Messaging account**; templates, billing and webhooks hang off it; the phone number hangs off a WAAC. Don't model "WABA owns number" as immutable; plan for `waac_id` (H1 2027) and `messaging_account_id` on sends (required H1 2027 for newest version).
6. **No number migration from Twilio anymore** on the new model — the customer *shares* the number via ES; Hay gets a fresh Messaging account with **zero templates**, so pre-seed the tenant's templates after onboarding. Throughput and tier are shared with Twilio while both are attached.
7. Webhook routing: key on `metadata.phone_number_id`, not `entry.id`; verify `X-Hub-Signature-256` over raw bytes; dedupe on `wamid` (retries for 7 days, fan-out to all subscribed apps). Status webhooks no longer include `conversation`/`pricing.billable` except FEP cases — bill/analyze from `pricing.type` + `pricing.category`.
8. `from`/`wa_id` may be **absent** (usernames). Key customers by BSUID; keep phone as optional metadata; handle `user_changed_user_id`. BSUIDs are portfolio-scoped so they aren't a global identity.
9. Media: webhook media IDs expire after **7 days** and signed URLs after **5 minutes** — download immediately into Hay's own storage. Download needs the Bearer header (no browser-direct links). Mind MIME mismatches (131053) and OGG-opus mono for voice.
10. Typing indicator is tied to an inbound `message_id`, auto-clears at 25 s, and the same call marks the message read — call it once when the agent starts generating, not on every token.
11. 24h window ≠ free. Outside it only templates; inside it service messages are billable past the free tier and utility templates are billable. Inbound calls also open the window.
12. Interactive limits: 3 reply buttons (title ≤20), lists ≤10 rows (title ≤24, desc ≤72), body ≤1024 for buttons / 4096 for lists; `reply.id` ≤256 is where to stash your intent payload.
13. Pair rate limit 1 msg/6 s per user (131056) — chunky AI answers must be coalesced, not streamed as many messages.
14. Display-name changes require a **re-register within 14 days** after approval, or nothing happens.
15. The onboarding cap (10/7 days until App Review + Business Verification → 200) will silently block growth — finish App Review before launch.
16. Don't `/deregister` coexistence numbers; don't try to disable 2FA via API; deregister/register limited to 10 per 72 h.
17. Error-code quick map: 131047 outside window → template; 131026 not a WhatsApp user/outdated client; 131049 marketing frequency cap; 131031/368 account restricted; 131042 billing problem; 132001 template missing/unapproved in that language; 132015/132016 template paused/disabled; 190 token revoked; 200/10 permission; 130429/80007/4 rate limits.
18. Policy: Hay's product is fine (business-specific support AI with human escalation), but a tenant pointing Hay at "answer anything" with no escalation path risks the number being restricted under both the AI-Providers clause and the escalation rule — enforce a human-handoff path in every WhatsApp-connected agent.
